# Zynez — TWA Android apps (Admin & Super Admin)

Two real **Trusted Web Activity** (TWA) Android apps, generated with
[Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap) (Google's
official TWA tooling). A TWA is not a WebView wrapper — it opens the
already-deployed website full-screen inside Chrome itself (via Custom
Tabs), with **no URL bar**, verified by
[Digital Asset Links](https://developers.google.com/digital-asset-links)
so Chrome trusts this app owns the site. There is no separate web
codebase here: both apps load the exact same deployed React app
(`Frontend/Ai_FE`) and backend as the browser, pinned to a different
starting route.

| App | Folder | Package ID | Launch URL |
|---|---|---|---|
| Admin (Company Admin) | `mobile-twa/admin` | `in.zynez.admin` | `https://zynex.mita.in/admin/login` |
| Super Admin | `mobile-twa/super-admin` | `in.zynez.superadmin` | `https://zynex.mita.in/super-admin/login` |

`zynex.mita.in` is the real, already-hosted production frontend — both
apps' `hostName`/`launchUrl` in `app/build.gradle` (generated from
`twa-manifest.json`) point at it. **⚠ See "Pending: redeploy the
frontend" below before installing either APK** — the production domain
is not yet serving the build these apps need.

Both were generated by `generate-twa.cjs` (drives `@bubblewrap/core`
directly, non-interactively) from `public/manifest-admin.webmanifest`
and `public/manifest-super-admin.webmanifest`. Each already has:

- A complete Android Studio / Gradle project (`app/build.gradle`,
  `AndroidManifest.xml`, launcher icons, splash screen) — confirmed to
  build (`BUILD SUCCESSFUL`, see below).
- Its own real signing keystore (`android.keystore` — **local/dev use**,
  see *Production signing* below).
- `twa-manifest.json`, the project's own config (edit + re-run
  `npx bubblewrap update` to regenerate, or just re-run
  `generate-twa.cjs`).

Role separation is enforced exactly like the website — client-side
(`AdminProtectedRoute` / `SuperAdminProtectedRoute`) and server-side
(`@super_admin_required` etc., `Backend/auth/auth.py`) role checks, keyed
off the signed-in account, not which app opened the page. A Company
Admin/User account manually navigating to `/super-admin/...` inside the
Admin app is redirected away exactly as on the website — there is
nothing app-side to keep in sync.

## Digital Asset Links (what makes the URL bar disappear)

`public/.well-known/assetlinks.json` was generated alongside both
projects — it lists **both** apps' package name + SHA256 certificate
fingerprint (from their signing keystores), since both point at the same
origin:

```json
[
  { "target": { "package_name": "in.zynez.admin", "sha256_cert_fingerprints": ["..."] } },
  { "target": { "package_name": "in.zynez.superadmin", "sha256_cert_fingerprints": ["..."] } }
]
```

This file **must be served at `https://<your-domain>/.well-known/assetlinks.json`**
— it already ships in `public/`, so any static host that serves the rest
of `dist/` (Apache with the existing `public/.htaccess`, Nginx, Vercel,
etc.) serves it automatically, over HTTPS, with no extra config — the
existing `.htaccess` rewrite rule already checks `-f`/`-d` (real
file/directory) before falling back to `index.html`, so
`.well-known/assetlinks.json` is served as the real file, never
swallowed by the SPA fallback. (If you switch hosts, double-check that
host doesn't hide dotfiles/dot-directories by default — a common way
this silently 404s elsewhere.) Confirm after deploying:

```bash
curl https://<your-domain>/.well-known/assetlinks.json
```

If Chrome can't fetch/match this file for the signing key the installed
APK was actually signed with, the TWA falls back to showing a URL bar
(a "yellow bar" warning) instead of failing — so this is safe to get
wrong during testing, but must be correct for a real release.

## App Links path scope — why each app only claims its own portal

Both `AndroidManifest.xml`s carry an `android:autoVerify="true"`
intent-filter — this is what lets Android treat `zynex.mita.in` links as
*this app's own*, not just what makes the TWA itself launch (that's a
separate mechanism: `LauncherActivity`'s hardcoded `DEFAULT_URL`
meta-data, which never goes through this intent-filter at all — the
TWA's own icon-tap launch is unaffected by anything below).

Bubblewrap's generated intent-filter scopes that `<data>` element to the
**host only** — `android:host="@string/hostName"`, no path restriction —
which claims *every* URL on the domain. With both apps installed and
verified, that meant opening `https://zynex.mita.in/admin/login` **in
plain Chrome** (not through either app) could get intercepted by
Android's OS-level link handling and handed to whichever app was
installed — including the wrong one, or even the public landing page —
instead of ever reaching Chrome's renderer. `generate-twa.cjs` now
patches this automatically after every `createTwaProject()` call
(`patchIntentFilterPathPrefix`), adding:

```xml
<data android:scheme="https"
    android:host="@string/hostName"
    android:pathPrefix="/admin/"          <!-- "/super-admin/" in that app -->
/>
```

so each app's OS-level link claim is scoped to its own portal only. A
plain Chrome visit to `/`, `/user/login`, or the *other* app's portal is
never intercepted by either app, even if both are installed — only a
URL actually under `/admin/*` (or `/super-admin/*`) is ever handed off,
and only to that specific app. Re-running `generate-twa.cjs` always
reapplies this (it throws loudly instead of silently skipping if
Bubblewrap's template ever changes shape and the patch no longer
matches — see the function's regex). Does not touch package IDs,
signing, or `assetlinks.json` — Digital Asset Link *ownership*
verification and intent-filter *path scope* are independent checks;
narrowing the latter changes nothing about the former.

## Production checklist

1. ~~Point everything at the real domain~~ — done. Both
   `twa-manifest.json` / `app/build.gradle` already use
   `hostName: 'zynex.mita.in'`, launch URLs
   `https://zynex.mita.in/admin/login` and
   `https://zynex.mita.in/super-admin/login`. To regenerate later (e.g.
   after an icon/branding change), re-run from `mobile-twa/`:
   ```bash
   cd Frontend/Ai_FE && npm run build && npx vite preview --port 4173
   cd mobile-twa && node generate-twa.cjs admin && node generate-twa.cjs super-admin
   ```
   (`generate-twa.cjs` reads manifest content from that local preview —
   see the comment at the top of the script — but writes the real
   `zynex.mita.in` host into the generated project regardless; edit
   `PRODUCTION_HOST` there directly if the domain ever changes.)
2. **Backend CORS** — not changed here (AWS-hosted, out of reach from
   this environment, and explicitly out of scope). `zynex.mita.in`
   already works as the site's own frontend origin today, so its backend
   almost certainly already allows it in `CORS_ALLOWED_ORIGINS` — the
   *local* `Backend/.env` in this repo only lists `localhost` origins
   (a dev-only file with no effect on the live AWS deployment), so there
   was nothing there to safely change. Confirm on the actual AWS
   instance's env if anything CORS-related misbehaves.
3. **Redeploy** — see the pending-redeploy note above; this is the one
   remaining step before either app is genuinely usable end-to-end.
4. **Production signing.** `mobile-twa/*/android.keystore` is
   git-ignored (see `.gitignore`) — `generate-twa.cjs` creates one
   locally the first time it runs for each app (password `zynezandroid`,
   see the script) if none exists yet, so every clone/environment gets
   its own working dev key with no secret ever traveling through git.
   That's fine for building, installing, and verifying Digital Asset
   Links today, but it is **not** your permanent Play Store signing
   identity. For a real release, generate your own keystore
   (`keytool -genkeypair ...`, or let Bubblewrap generate one with your
   own organization details), keep it somewhere safe outside version
   control, and re-run the generator pointing `signingKey.path` at it —
   then regenerate `assetlinks.json` from *that* key's fingerprint.
   **Never commit a production signing key.**

## Building

```bash
cd Frontend/Ai_FE/mobile-twa/admin      # or mobile-twa/super-admin
./gradlew assembleDebug                 # -> app/build/outputs/apk/debug/app-debug.apk
adb install -r app/build/outputs/apk/debug/app-debug.apk

# Release (signed with this project's own keystore, from twa-manifest.json):
./gradlew assembleRelease
```

`npx bubblewrap build` (run from inside `mobile-twa/admin` or
`mobile-twa/super-admin`) does the same thing via the official CLI, and
`npx bubblewrap install` builds + installs to a connected device in one
step — both read the same `twa-manifest.json` already in place.

## Super Admin push notifications

The Super Admin "New Lead" push notifications (Firebase Cloud Messaging
— see `Backend/notifications/FCM_SETUP.md`) need **no changes to this
TWA project at all**: a TWA is Chrome itself rendering
`zynex.mita.in`, sharing that origin's real browser storage/service-
worker registrations — so notification permission, the service worker,
and delivery while backgrounded/closed all work exactly as they do in a
normal Chrome tab, with nothing native to configure.

One optional, purely cosmetic upgrade: by default a notification shown
this way is attributed to "Chrome," not "Zynez Super Admin" — Google's
[Notification Delegation](https://developers.google.com/codelabs/notification-delegation)
(the `androidbrowserhelper` `TrustedWebActivityService`) can re-brand it
under the app's own name/icon instead. Not implemented here — it needs
native code added to the generated Android project (re-applied on every
regeneration) for a UI-only improvement with no functional difference in
whether/when the notification arrives.
